## 2. Why this script exists

The local `gh` CLI in this dev environment is **v0.11.0 (2020-07-16)**. Both the `gh issue comment` subcommand (added in 2.x) and the `--body` flag are unavailable. Phase 16's mitigation was a copy-paste Markdown deliverable, which works but is tedious for 8 issues. Phase 16.5 ships a small standalone Python script that:

1. Parses `plans/16_github_replies.md` (the **single source of truth** for issue replies — Phase 16 already wrote it).
2. For each issue, makes two REST calls:
   - `POST /repos/{owner}/{repo}/issues/{n}/comments` to publish the reply.
   - `PATCH /repos/{owner}/{repo}/issues/{n}` with `{"state": "closed"}` to close.
3. Prompts for confirmation before each issue so the operator can step through one at a time.

No new R or Python dependencies — Python 3 stdlib (`urllib.request`, `json`, `argparse`, `re`, `os`, `sys`) is sufficient.

## 3. Script anatomy

`plans/close_issues.py` — 215 lines, 4 logical sections.

### 3a. Markdown parser (`parse_issues`)

The Phase-16 Markdown wraps each reply body in a `` ```markdown `` ... `` ``` `` fence. Several reply bodies contain nested fences, including:

- `` ```r `` ... `` ``` `` — language-tagged R code blocks.
- `` ``` `` ... `` ``` `` — **unlabeled** code blocks (e.g. the `LOW_OVERLAP_WARN` log snippet in #66's body).

A naive "first `` ``` `` after `` ```markdown `` is the closer" parser truncates at the first nested fence. A fence-depth tracker (which I tried first) fails on bare-bare nested fences because both opener and closer match the same syntax — so the depth counter false-positives.

**The robust rule** the script uses: the OUTER closer is the **last** line matching `^\s*```\s*$` between the `### Issue #N` header that starts this block and the next `### Issue #N` header (or EOF). Everything between the outer opener (exclusive) and outer closer (exclusive) is the body, verbatim.

This works because nested fences inside the body always come in matched open-close pairs that don't change the position of the LAST bare `` ``` `` in the section.

Sanity-checked against all 8 issues — body sizes:

```
#100  1929 chars   #94   1784 chars
#92   1489 chars   #66   1339 chars
#76   1558 chars   #65    963 chars
#89    987 chars   #42   1137 chars
```

#66's body correctly captures the inner `WARN: LOW_OVERLAP_WARN: ...` snippet AND the inner `` ```r `` recommended-workflow block AND the closing `Closing as fixed; please reopen if the warning doesn't fire on a case you expect.` paragraph — the parts the fence-depth parser was truncating.

### 3b. REST API helpers (`post_comment`, `close_issue`)

Two thin `urllib.request.Request` wrappers around `_request(token, url, method, payload)`. Headers used per GitHub's [REST API docs](https://docs.github.com/en/rest):

```
Authorization:           Bearer $GITHUB_TOKEN
Accept:                  application/vnd.github+json
X-GitHub-Api-Version:    2022-11-28
Content-Type:            application/json
User-Agent:              sangeranalyseR-close_issues.py
```

Errors are caught at `urllib.error.HTTPError` granularity; the script prints `HTTP <code> — <truncated response body>` and continues to the next issue. A summary at the end lists all failures with re-run instructions.

### 3c. CLI driver (`main`)

`argparse`-based:

| Flag               | Purpose                                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------- |
| `--dry-run`         | Parse + preview; no API calls. Use this **first** every time.                                             |
| `--issue N`         | Process only issue `N` (e.g. `--issue 65`). Use to retry one failure or to do a low-stakes test run.      |
| `--no-confirm`      | Skip the per-issue `input()` prompt. Marked DANGEROUS in `--help` — irreversible.                          |
| `--md PATH`         | Override the input file path; defaults to `plans/16_github_replies.md`.                                   |

### 3d. Safety controls

- **Token check first.** Script exits with code 2 + a clear "set GITHUB_TOKEN" message if the env var is missing, even before any parsing-error handling.
- **Confirmation prompt before every issue.** `KeyboardInterrupt` exits with code 130 (the standard Ctrl+C convention).
- **Failures don't cascade.** A failed comment skips that issue's close call; subsequent issues still run.
- **Idempotency note in the docstring.** Re-running the script on an already-commented issue posts a duplicate comment; the close is a no-op. The dry-run + per-issue prompt mitigates this.

## 5. Usage (for the operator)

```bash
# 1. Create a Personal Access Token at:
#      https://github.com/settings/tokens
#    Required scope: `public_repo` (sufficient for public repositories).

# 2. Export it:
export GITHUB_TOKEN=ghp_xxxxxxxxxxxxxxxxxxxx

# 3. Dry-run first — confirm 8 issues parse cleanly with the right
#    first-line previews:
python3 plans/close_issues.py --dry-run

# 4. (Optional) Test on one low-stakes issue first:
python3 plans/close_issues.py --issue 65

# 5. Live run — steps through all 8 issues with per-issue prompts:
python3 plans/close_issues.py
```

If a single issue fails (transient HTTP error, etc.), re-run with `--issue <N>` for that one. **Do not** re-run the whole script — GitHub's API has no comment-replacement endpoint, so a re-run posts duplicate comments.

## 7. Non-goals (deferred)

- An R / `httr2` version of the script. Same functionality, more deps.
- A retry / exponential-backoff loop. 8 issues × 2 endpoints = 16 requests; if any fail the operator can re-run with `--issue <N>`.
- Auto-discovery of new issues to close. The script is intentionally driven from the explicit `16_github_replies.md` whitelist — never closes issues we haven't drafted a reply for.
- Comment-replacement support. GitHub's API doesn't offer it (only edit-by-comment-id, which would require capturing the prior comment IDs); not worth building until we hit a re-run scenario.
